# 수행 계획 — 채용 파이프라인 보드

> 착수 시점에 요구사항을 기능 단위로 분해하고 스택·설계 방향을 정한 문서.
> 진행 상태는 [`PROGRESS.md`](../PROGRESS.md), 작업 규칙은 [`CLAUDE.md`](../CLAUDE.md)에 있다.

## 1. 요구사항 정리

채용 담당자가 지원자를 단계별로 관리하는 파이프라인 보드.
단계: `서류검토 → 면접 → 처우협의 → 최종합격 / 불합격`. 실제 백엔드 없이 mock API로 읽고 쓴다.

### 필수 (Must)

| # | 요구사항 | 핵심 판단 지점 |
|---|---|---|
| 1 | 보드/컬럼/카드 — 이름·직무·지원일·현재 단계 표시 | — |
| 2 | 단계 이동 — mock API에 저장되어 **새로고침 후에도 유지** | mock 저장소를 인메모리로 두면 이 조건이 깨진다 |
| 3 | **낙관적 업데이트** — UI 선반영, 실패 시 원상 복구 + 피드백 | mock API가 약 15% 확률로 실패한다 |
| 4 | 검색(이름)/필터(직무) — 200건 이상에서 체감 지연 없이 | 입력 지연과 목록 렌더를 분리해야 한다 |
| 5 | 상세 보기 — 사이드 패널 | 포커스 관리가 따라온다 |
| 6 | 로딩 / 에러 / 빈 상태 3종 UI | 빈 상태는 "데이터 없음"과 "검색 결과 없음"이 다르다 |

### 도전 (Should)

| 항목 | 접근 |
|---|---|
| 경쟁 상태 | 같은 카드 연속 이동 시 데이터가 깨지지 않아야 함 → 카드별 직렬 큐 + seq 기반 stale 응답 폐기 |
| 대량 데이터 | 1,000건 기준 스크롤/필터가 부드러워야 함 → 컬럼 단위 가상 스크롤 |
| 되돌리기 | 방금 한 이동 취소 → 낙관적 경로를 그대로 재사용 |
| 테스트 | 낙관적 업데이트 롤백 등 핵심 로직 |
| 웹 접근성 | 키보드만으로 단계 이동과 상세 열람 가능 |

### 이 과제의 난이도가 실제로 걸려 있는 곳

요구사항 3(낙관적 업데이트)과 도전 과제(경쟁 상태)가 만나는 지점이다.

낙관적 업데이트는 **"UI는 됐다고 말하는데 서버는 실패한 상태"**를 의도적으로 만든다.
여기에 15% 실패율과 200~800ms 지연이 겹치면, 사용자가 같은 카드를 빠르게 두 번 옮겼을 때
**어느 상태로 되돌려야 하는가**가 자명하지 않다.

흔한 구현(전체 캐시 스냅샷을 잡았다가 실패 시 복원)은 여기서 깨진다.
두 번째 요청이 스냅샷을 잡는 시점에는 이미 첫 번째의 낙관적 변경이 반영되어 있어서,
첫 번째가 실패하면 **한 단계가 아니라 두 단계 전으로 되돌아간다.**

→ 롤백을 **필드 단위**로 좁히고, 같은 카드의 이동을 **직렬화**하며,
   늦게 도착한 응답을 **시퀀스로 폐기**하는 세 가지를 직접 구현한다.

설계 원칙은 하나다. **늦게 도착한 서버 응답이 사용자의 최신 조작을 덮어쓰지 않는다.**

## 2. 기술 선택과 근거

| 항목 | 선택 | 근거 |
|---|---|---|
| 빌드/프레임워크 | Vite + React 19 + TS | 순수 클라이언트 상태 문제라 SSR의 이점이 없다. mock 계층도 브라우저 한 곳만 보면 된다 |
| 서버 상태 | TanStack Query v5 | 캐시·dedup·mutation 생명주기 훅 지점을 얻되, **조정 로직은 직접 소유**한다 (§3) |
| 클라이언트 상태 | `useState` / `useReducer` | 필터·선택 카드·Undo 스택뿐. 전역 스토어를 도입할 규모가 아니다 |
| mock API | MSW | `npm run dev` 하나로 실행되고 **배포된 정적 사이트에서도 그대로 동작**한다. json-server는 별도 프로세스가 필요해 확인 비용이 늘어난다 |
| 가상 스크롤 | `@tanstack/react-virtual` | 렌더링만 담당하는 얇은 라이브러리. 상태 로직을 가져가지 않는다 |
| 테스트 | Vitest + Testing Library | 롤백·경쟁 상태를 결정론적으로 재현 |
| 단계 이동 | **액션 버튼 + 키보드** | 아래 참조 |

### 왜 드래그앤드롭이 아니라 액션 버튼인가

요구사항이 둘 중 택1이고, DnD를 택하면 **키보드 대체 경로가 필수**로 따라온다.
즉 DnD를 택해도 버튼/키보드 경로는 어차피 만들어야 한다.

액션 버튼을 1차 수단으로 두면 키보드 조작이 UI의 우회로가 아니라 **같은 경로**가 되고,
접근성이 나중에 덧붙이는 기능이 아니라 기본 동작이 된다.
DnD는 시간이 남으면 별도 커밋으로 얹는다.

### TanStack Query의 경계

라이브러리가 핵심 상태 로직을 통째로 대신하지 않도록 경계를 명시한다.

| 라이브러리에 맡기는 것 | 직접 구현하는 것 |
|---|---|
| 캐시·dedup·`onMutate/onError/onSettled` 훅 지점 | **카드별 직렬 큐** (`moveQueue.ts`) |
| `cancelQueries` | **seq 기반 stale 응답 폐기** |
| 재시도 정책 | **필드 단위 롤백** |

## 3. mock API 설계

```
src/mocks/
├── browser.ts     setupWorker (개발/배포)
├── server.ts      setupServer (테스트)
├── handlers.ts    GET /api/candidates, PATCH /api/candidates/:id/stage
├── db.ts          localStorage 백킹 저장소
└── seed.ts        지원자 1,000건 생성
```

- 지연 **200~800ms 랜덤**, 실패 **약 15%** (요구 조건)
- `PATCH` 성공 시 갱신된 카드 + `updatedAt` 반환 → stale 응답 판별 근거
- 실패 시 `503` + `{ code, message }`
- **지연·실패율을 URL 쿼리로 오버라이드 가능하게** 한다.
  실패를 눈으로 확인하려면 확률 15%를 기다릴 게 아니라 100%로 강제할 수 있어야 한다.
- 저장소는 **localStorage에 백킹**한다. 인메모리만 쓰면 새로고침 시 초기화되어 필수 요구사항 2가 깨진다.

## 4. 기능 단위 분해와 커밋 순서

`기능 하나 = 커밋 하나 = 기록 한 섹션` 원칙으로 진행한다.
전체 목록과 진행 상태는 [`PROGRESS.md`](../PROGRESS.md)에 있다.

```
setup → mock-api → board-layout → card-list → loading-error-empty
      → stage-move → optimistic-update → race-condition → test
      → search-filter → detail-panel → a11y-keyboard
      → virtualization → undo → docs
```

의존 관계상 mock API를 먼저 세우고, 낙관적 업데이트 → 경쟁 상태 → 테스트를 연속으로 붙인다.
검색/필터와 상세 패널은 보드가 안정된 뒤에 얹는다.
가상 스크롤은 **마지막에** 넣는다 — 포커스 관리와 충돌할 수 있어 a11y가 자리 잡은 뒤여야 한다.

## 5. AI 협업 방식

작업 규칙 전문은 [`CLAUDE.md`](../CLAUDE.md)에 있다. 요지는 세 가지다.

**1. 검증 강도를 기능마다 다르게 둔다.**
전부에 같은 검증을 도는 것은 비용만 늘고 형식적이 된다.
낙관적 업데이트·경쟁 상태·접근성·가상 스크롤은 풀 검증, 레이아웃·카드 같은 것은 코드 정독으로 끝낸다.

**2. 리뷰는 다른 벤더 모델에게 맡긴다.**
같은 모델 계열에게 자기가 만든 걸 리뷰시키면 자기 편향이 생긴다. 자기가 놓친 건 다시 봐도 놓친다.
그래서 핵심 구간은 `codex` CLI를 호출해 **반박만 하도록** 지시한다.
사람 팀에서 코드 리뷰를 남에게 맡기는 것과 같은 이유다.

**3. "완료했습니다"를 믿지 않고 실제로 눌러본다.**
코드가 컴파일되는 것과 화면이 동작하는 것은 다르다.
Playwright로 실제 화면을 띄워 조작하고, 특히 **실패율을 100%로 강제해 롤백을 눈으로 확인**한다.

이 과제에서 이 원칙이 특별히 중요한 이유가 있다.
**가장 위험한 실패는 에러가 나는 것이 아니라 "됐다"고 말하는 것**인데,
낙관적 업데이트는 그 상태를 UI가 의도적으로 만들어내는 기능이기 때문이다.
검증을 실행으로 하지 않으면 이 기능은 "되는 것처럼 보이는" 채로 통과한다.

커밋은 자동화하지 않는다. 반복은 자동화하고 판단은 사람이 한다.

# 채용 파이프라인 보드

지원자를 채용 단계별로 관리하는 보드. 카드를 단계 간 이동시키며, 데이터는 mock API로 읽고 쓴다.

> **이 과제에서 가장 위험한 실패는 에러가 나는 것이 아니라 "됐다"고 말하는 것이었다.**
>
> 낙관적 업데이트는 UI가 먼저 "옮겨졌다"고 말하는 기능이다. 그런데 서버는 15% 확률로 실패하고
> 응답은 200~800ms 뒤에 온다. 그 사이 사용자는 계속 조작한다.
> 그래서 이 저장소의 작업 대부분은 **화면이 말하는 것과 서버의 실제 상태를 어긋나지 않게 하는 일**이었다.
> 판단 과정은 [`DECISIONS.md`](./DECISIONS.md)와 [`PROMPTS.md`](./PROMPTS.md)에 있다.

**배포**: https://dygreen.github.io/hiring-pipeline-board/

## 실행

```bash
npm install
npm run dev
```

기본 포트는 **5173**이다. 사용 중이면 Vite가 다음 빈 포트로 옮기고 터미널에 실제 주소를 찍는다.

**URL 파라미터는 모두 선택이다.** 아무것도 붙이지 않으면 과제 조건 그대로 동작한다 —
지연 200~800ms, 실패 약 15%. 새로고침을 몇 번 하면 자연스럽게 실패 화면을 만나게 된다.

## 스택

- **Vite + React 19 + TypeScript**
- **MSW** — mock API (지연 200~800ms, 실패 약 15%). 저장은 localStorage 백킹
- **TanStack Query v5** — 서버 상태. 단 **이동 요청의 순서 제어와 롤백은 직접 구현**했다 ([이유](./DECISIONS.md#1-낙관적-업데이트--공식-레시피의-전체-스냅샷-롤백을-쓰지-않았다))
- **@tanstack/react-virtual** — 컬럼 가상 스크롤
- **Vitest + Testing Library** — 롤백·경쟁 상태 테스트

## 구현 범위

### 필수

- [x] 보드/컬럼/카드 — 이름·직무·지원일·현재 단계
- [x] 단계 이동 — 액션 버튼 + 키보드, mock API에 저장되어 새로고침 후에도 유지
- [x] 낙관적 업데이트 — UI 선반영, 실패 시 원상 복구 + 토스트

- [x] 상세 보기 — 사이드 패널
- [x] 로딩 / 에러 / 빈 상태

### 도전

- [x] 경쟁 상태 처리 — 카드별 직렬 큐 + 요청 순번 + 확정 단계 기준 롤백
- [x] 대량 데이터 — 1,000건 컬럼 가상 스크롤
- [x] 되돌리기 — 토스트 버튼 + `Cmd/Ctrl+Z`
- [x] 테스트 — 롤백·경쟁 상태·큐 순서 16개
- [x] 웹 접근성 — 키보드만으로 전 기능 조작

드래그앤드롭은 구현하지 않았다. 요구사항의 택1에서 액션 버튼을 골랐고,
[그 판단의 근거](./DECISIONS.md#3-드래그앤드롭-대신-액션-버튼--키보드)를 적어두었다.

## 키보드 조작

**마우스 없이 전 기능을 쓸 수 있다.**

| 키                   | 동작                                            |
| -------------------- | ----------------------------------------------- |
| `Tab`                | 컬럼 간 이동                                    |
| `↑` `↓`              | 같은 컬럼 안에서 카드 이동                      |
| `←` `→`              | **단계 옮기기**                                 |
| `Home` `End`         | 컬럼의 처음 / 마지막 카드                       |
| `Enter` `Space`      | 상세 열기                                       |
| `Esc`                | 상세 닫기                                       |
| `Delete` `Backspace` | 불합격 처리                                     |
| `Cmd/Ctrl` + `Z`     | 되돌리기 (입력창에서는 텍스트 실행 취소가 우선) |

컬럼당 카드 하나만 `Tab` 대상이 된다(roving tabindex).
전부 `Tab` 순서에 두면 1,000건 기준 **마지막 카드까지 4,000번**을 눌러야 한다.

## 동작 확인용 파라미터

기본 동작에는 필요 없다. 확률에 기대지 않고 특정 상황을 재현할 때 쓴다.

| 파라미터           | 동작                                                     |
| ------------------ | -------------------------------------------------------- |
| `?moveFailRate=1`  | 목록은 정상, **이동만 실패** — 롤백을 눈으로 보려면 이것 |
| `?fetchFailRate=1` | 목록 조회만 실패 — 에러 화면 확인                        |
| `?failRate=0`      | 모두 성공                                                |
| `?failRate=1`      | 모두 실패                                                |
| `?delay=0`         | 지연 없음                                                |
| `?reset=1`         | 저장소를 비우고 다시 시드                                |

배포본에도 그대로 붙는다. 예: `https://dygreen.github.io/hiring-pipeline-board/?moveFailRate=1`

**롤백을 확인하려면**: `?moveFailRate=1`로 접속 → 카드의 이동 버튼 클릭 →
즉시 옮겨졌다가 제자리로 돌아오고 토스트가 뜬다.

**경쟁 상태를 확인하려면**: `?moveFailRate=1&delay=500`으로 접속 →
한 카드에서 `면접 →` 누르고 바로 `처우협의 →` 클릭 →
둘 다 실패하지만 **처음 단계로** 돌아온다. 중간에 잠깐 보였던 단계로 남지 않는다.
그 단계는 서버에 한 번도 저장된 적이 없기 때문이다.

## 성능

1,000건 기준. 같은 조건에서 해당 구현만 되돌려 A/B로 측정했다.

| 항목                                     |      적용 전 |            적용 후 |
| ---------------------------------------- | -----------: | -----------------: |
| 검색 입력 최대 지연 (`useDeferredValue`) |        156ms |               58ms |
| 검색 입력 최대 지연 (가상 스크롤까지)    |        147ms |           **44ms** |
| 롱태스크(50ms 초과)                      | 155ms · 81ms |           **없음** |
| 전체 DOM 노드                            |       13,081 |            **996** |
| 렌더된 카드                              |        1,000 | **65** (컬럼당 13) |

## AI 협업 세팅

이 저장소에는 AI 도구가 읽는 파일이 세 개 있다.
세션이 끊겨도, 다른 도구로 열어도 같은 규칙으로 작업이 이어지게 하기 위한 것이다.

| 파일                           | 역할                                                          |
| ------------------------------ | ------------------------------------------------------------- |
| [`CLAUDE.md`](./CLAUDE.md)     | **규칙 정본.** 금지 항목, 아키텍처 경계, 검증 절차, 커밋 규약 |
| [`AGENTS.md`](./AGENTS.md)     | Codex·Cursor 등의 진입점. 정본을 가리키는 포인터              |
| [`PROGRESS.md`](./PROGRESS.md) | 진행 상태, 열린 이슈, 확정한 가정, 측정 기록                  |

규칙을 두 벌로 유지하지 않는다. 한쪽만 고쳐지면 어느 쪽이 정본인지 알 수 없게 되기 때문에,
정본은 `CLAUDE.md` 하나이고 나머지는 얇게 유지한다.

구현은 Claude Code로, 핵심 구간의 리뷰는 **다른 벤더의 CLI(`codex`)** 로 맡겼다.
같은 모델에게 자기가 만든 걸 리뷰시키면 자기 편향이 생긴다 —
자기가 놓친 건 다시 봐도 놓친다. [실제로 잡아낸 것들](./DECISIONS.md#6-ai-협업-방식--검증-강도를-나누고-리뷰는-다른-벤더에게-맡겼다)을 적어두었다.
